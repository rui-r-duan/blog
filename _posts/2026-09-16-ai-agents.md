People agree that **Agent = LLM + tools**, and **harness engineering**
is the way to keep LLM's responses on track.  I provide a different
view on AI agents and harness engineering.  In particular, all the
agentic AI related technologies can be uniformly explained by
programming language knowledge.

Most learning materials stack terms and buzz words, such as loop
engineering, harness engineering, Skills, MCPs, RAG, plugins,
autonomous, workflow, thinking, inference, reasoning, etc., and they
use wrappers like LangChain framework or OpenAI/Anthropic/Google SDKs
to explain things.  In this article I avoid using those terms and the
wrapper frameworks.  Instead, I demystify AI agents at a low level.

When people talk about AI agents, it may refer to two different
things: a **program** or a **configuration**.  An agent program is a
complete executable program which may run in your local machine, or
run in a remote server.  An agent in an agent program is a
configuration of system prompt and available tools and so on.

I will discuss AI agent programs and configurations, harness
engineering, MCPs, Skills, RAG, sub-agents, and multi-agents.

Note: all the code in this article are Python-like pseudo-code.

# Agent program

The nature of an AI agent program is to use the LLM's probablistic
prediction to express some `if-else` logic.  This is the major
difference between an agent program and a traditional program.

First of all, an LLM invocation is a **pure function call** `y = p(x)`
where `x` is the prompt, `p` is the LLM's `predict` function which is
usually implemented in the inference engine, `y` is the response.  It
has no state.  It has no side effect, which means it does not change
any external state of the program.  Thus, using LLM is like
**functional style programming**.

Secondly, an agent is a **stateful** program which uses some LLM
invocations.  "Stateful" implies that the state of the program will be
changed, so the next run's output state may be different from the
first run's, for example, a robot's arm position is changed, or a
database table is altered.  When `if-else` bloats to the extent that
there are too many cases to handle so it is impractical to write
`if-else`, it is the right place to use the LLM invocations to replace
the deterministic `if-else` expressions.  Now the program becomes an
AI agent.

[![Deterministic program v.s. AI agent program]({{ "/images/ai/ai_agent_nature.svg" | relative_url }})]({{ "/images/ai/ai_agent_nature.svg" | relative_url }})

Thirdly, to control the LLM's context window usage and to handle the
unexpected responses and unexpected LLM invocation errors, we have to
wrap the LLM invocations with lots of `if-else`.  **This is the nature
of harness engineering, nothing special.**

The following diagram introduces four common harness patterns.

The `if-else` before the LLM invocation controls the input prompt `x`
for `y = p(x)`, the `if-else` after the LLM invocation does the
exception handling, including retries, new prompt `x'`, fallback to
deterministic `if-else` business logic, handling **context degradation
(context rot)**, etc..

tool use can be considered as a kind of harness.  Its purpose is
to add more information to the context, and pass the new context to
the LLM.  The tool may have side effects which change external states.
When LLM returns a tool use request, it expects an answer in the
next turn.

The nature of memory engineering is to store the conversation history
in a detailed or compact form somewhere (in memory or persistent
storage, local or remote, etc.).

## How to define a tool?

The previous example provides a very simple way to tell LLM that the
tool looks like that and should be called (used) by providing an empty
JSON object `{}`.  That one was defined in the system message.

However LLM may sometimes fail to think of the tools, because it does
not say how to use the dict type parameter, it has many mysterious
things that are not expressed explicitly.

Remember, LLM only understands token sequence (text block).  LLMs need
a kind of text format to identify a text block as a tool definition,
and to know how to use it, in what condition.

To let the LLM understand the tool's specification much better and
thus increase the the correct tool use accuracy , LLM engineers think
of a way to do the specification: JSON schema.  They train the LLM to
pay special attention to the "tools" keyword and a pre-defined JSON
schema.  The main idea is to help LLM identify: "Oh, this is a tool
(like a function)!"

The popular LLM models all adopt some kinds of JSON schemas that
define a tool like a programming language function.

A famous example is `get_weather()`.  In Anthropic API format, the
tool is defined like this:

```json
{
  "tools": [
    {
      "name": "get_weather",
      "description": "Get the current weather in a given location",
      "input_schema": {
        "type": "object",
        "properties": {
          "location": {
            "type": "string",
            "description": "The city and state, e.g. San Francisco, CA"
          },
          "unit": {
            "type": "string",
            "enum": ["celsius", "fahrenheit"],
            "description": "The unit of temperature"
          }
        },
        "required": ["location"]
      },
      "input_examples": [
        {"location": "San Francisco, CA", "unit": "fahrenheit"},
        {"location": "Tokyo, Japan", "unit": "celsius"},
        {"location": "New York, NY"}
      ]
    }
  ]
}
```

It is equivalent to the following Rust type definition and function
definition:

```rust
pub enum TemperatureUnit {
    Celsius,
    Fahrenheit,
}

pub struct WeatherArgs {
    pub location: String,
    pub unit: Option<TemperatureUnit>,
}

fn get_weather(p: WeatherArgs) -> String
```

In the JSON text, every word is important, including the function name
and the description.  The function name, the parameter name and type,
and the description can help LLM pick the tool for the right
situations.

## How are LLMs trained to know tool use?

This "behaviour" is trained in the post-training.  There are two main
methods: **supervised fine-tuning (SFT)** and **reinforcement learning
(RL)**.  The consequence is that when LLM sees your question about the
weather of a location, it knows to call the `get_weather()` tool.

## Best practices to handle tool use errors

Like what we handle errors in Rust using `Result<T>` and `Option<T>`,
we need to pass the errors to the LLM based on the similar idea:
explicitly passing the error as data, that is to pass an informative
string to describe the error type and error details, so that the LLM
will respond with appropricate next step.

We must differenticate the following 5 categories of result, and
explicitly tell the LLM the error information.

- tool output
    - success
      - non-empty result

        e.g. a JSON object `{"name": "John Doe"}` or `["apple", "banana", "pear"]`

      - empty result

        e.g. `null` or empty array `[]` in JSON

  - failure

    - access failure

      e.g.
```python
f"ACCESS_FAILURE: Billing API is unreachable ({exc}). "
"The lookup was attempted but could not complete. "
"Treat this billing history as unknown, not as empty."
```

    - validation error

      e.g.
```python
"VALIDATION_ERROR: account_id must begin with 'ACC-' (received: "
f"'{account_id}'). Example of a valid value: 'ACC-00123'."
```

    - permission denied

      e.g.
```python
"PERMISSION_DENIED: Billing history requires billing_admin or support_tier2 "
f"role. Caller role '{caller_role}' is not authorized. "
"Escalate to a billing team member to retrieve this information."
```

# Prompt is the key

LLM is `y = p(x)` where x is the prompt.  Insturctions are prompts,
system role messages are prompts, user role messages are prompts, tool
definitions are prompts, LLM's answers (role "asisstant") are prompts
for the next turn, tool use requests are prompts, ...

Do you see that the key to use LLMs is to compose a good prompt `x`?

```
x = a + a' + b + b' + c + c' + d ...
```

**To master AI agent programming, the most important thing is to
understand an LLM's characteristics, and to compose good prompts!**
The harness will come natually from the understanding.

**Example characteristics and experiences**:
- Compare how well LLMs follow your instructions.
- Pay attention to token usage when requests scales, for example,
  additional examples × 80 tokens each = 320 extra input tokens per
  call × 500,000 calls per day = 160 million additional input tokens
  per day.
- context degradation effect
- the **U-shape attention distribution** and the **loss-in-the-middle
  phenomenon**, see this paper `"Lost in the Middle: How Language
  Models Use Long Contexts" by Nelson F. Liu, Kevin Lin, Peter West,
  Irwin King, and Noah A. Smith (originally published in July 2023 and
  featured in TACL)`
- Tool selection degrades significantly beyond roughly 5 tools per
  agent. Distribute the tools across multiple specialized subagents,
  each with a focused set.
- Claude may request multiple `tool_use` in one turn, expecting a list
  of `tool_result` user role message which contains a list of
  `tool_result` objects.
- A negative example helps fix a classification mistake.
- Few-shot examples help.
- A routing task is pattern matching, enabling extended thinking may
  cause Claude to deliberate unnecessarily and sometimes override its
  initial correct classification, the consenquence is a drop in
  accuracy.
- It is a good practice to defend malicious prompt (prompt injection)
  by wrapping the data (especially tool result) in XML tags, and
  prompt telling the LLM to treat the content in the XML tags as data
  but not directives to follow, and check the result for known
  injection phrases.
- Explicit hard language helps ("never", "regardless of how the
  request is framed").

**How to provide appropriate context?  There are many ways.  MCPs,
Skills, and RAG are three wide adopted approaches.**

# MCPs

Model Context Protocol (MCP) is a communication protocol to supply a
set of tool definitions and other contextual information for an agent
program to use in the LLM context.

The nature of MCP is an adaptor that bridges the tool implementation
and the tool users.  We can think of it as a set of Remote Procedure
Calls (RPC), so they are also like function calls.

## scalability problem
Remember that a tool's implementation has two parts:
- tool declaration (like function declaration, the LLM must initiate a
  tool use that complies with the declaration)
- tool implementation (like function implementation)

Without MCP, to connect to a data source (e.g. PostgreSQL):
```
agent A (Python/LangGraph):     tool decl A, tool impl A
agent B (TypeScript):           tool decl B, tool impl B
agent C (Rust):                 tool decl C, tool impl C
...
agent M (iOS):                  tool decl M, tool impl M
```

Each agent must have its own implementation.

If we have `N` data sources, then we must have `M × N`
implementations.

Even if we publish a standardized tool declaration for PostgreSQL,
there has to be `M` different implementations for `M` clients.  For `N` data sources, we still need `M × N` implementations.

```
agent A (Python/LangGraph):   tool impl A ---+
agent B (TypeScript):         tool impl B ---+
agent C (Rust):               tool impl C ---+---▶ unified decl
...                                          |
agent M (iOS):                tool impl M ---+
```

With MCP, all the `M` clients can share the same implementation (server) for PostgreSQL.
```
agent A ---+             +---------------------------------+
agent B ---+             |                                 |
agent C ---+---(MCP)---▶ | unified decl --- unified impl   |
...        |             |                                 |
agent M ---+             +---------------------------------+
                                     MCP Server
```

Thus, for `N` data sources, we only need `N` implementations, no matter how many clients there are.

## Primitives

MCP is used to advertise the capabilities of a server for a data
source.  It uses JSON-RPC to expose three primitives.  MCP clients
will use the `*/list` methods (e.g. `tools/list`) to discover
available primitives.

- Tools: Executable functions that AI applications can invoke to
  perform actions (e.g., file operations, API calls, database queries)
  
- Resources: Data sources that provide contextual information to AI
  applications (e.g., file contents, database records, API responses)
  
  This is like a Skill which will be discussed below.

- Prompts: Reusable templates that help structure interactions with
  language models (e.g., system prompts, few-shot examples)
  
  This is like a Skill which will be discussed below.

# Skills

Claude style Skills are a kind of product of prompt engineering and
software engineering.  The key idea is to find and load prompts from
the file system.  It has lots of conventions to make the Skill system
work effectively.

Skills run in agent programs.

A skill's definition includes prompts (instructions, templates,
examples, etc.) and optional code.  Explicit instructions are provided
about how to run the associated code.  They are stored in a directory
of the file system, either in your local machine or in a remote
server.

How does a skill work in an agent program?

```
  STARTUP: agent program loads skill metadata: name + description only

→ RELEVANCE DECISION:
  -----------------------------------------
  |  y = p(skill_metadata + user_request) |
  -----------------------------------------
  if LLM thinks a skill is relevant to the request,
    it requests the skill to be loaded

→ LOAD SKILL INSTRUCTIONS: the agent program uses a tool to read
    SKILL.md file, and loads it into context

---------------- LOOP BEGIN ----------------

→
  ----------------------------------------------------------------
  | y = p(skill_metadata + user_request + skill_prompt + ...)    | ◀-----+
  ----------------------------------------------------------------       |
  LLM decides if the GOAL IS REACHED or STEPS ARE DONE                   |
                                                                         |
  if DONE                                                                |
    - output y, END                                                      |
                                                                         |
  else                                                                   |
    - y contains a tool_use request                                      |
    - agent program calls the tool                                       |
    - agent program appends tool call result to the context, and LOOP ---+

---------------- LOOP END ----------------
```

What essential tools will be called in a skill system?  The following
tools are necessary for a Skill system.

- bash_code_execution: used to run a program, e.g. `python some.py`
- text_editor_code_execution: view, create, edit files (string replace)

They are provided by the agent program, e.g. Claude Code, or Claude.ai
Web app.

Claude Code runs the Skill invoked tools on the local machine.
Claude.ai runs the Skill invoked tools in a remote server's container.

CONCLUSION:

- prompt driven
- advanced by tool uses
- You can put anything in SKILL.md, and it can reference other files
  in the skill directory in the file system.
- maily used to implement a workflow (an algorithm)

# RAG

The purpose of Retrieval-Augmented Generation (RAG) is to provide only
the relevant fragments of data to the LLM context.  The user asks a
question to your system, your system searches the vector database to
find the relevant chunks of data, select the best chunk or chunks
according to the criteria that you set, then feed the selected data to
the LLM context. That's it.

How to find the relevant data?  By comparing the similarity.  How?  By
transforming the search target text and the document text into the
so-called `embeddings`, then it is easy to calculate their similarity
level in the `embedding` vector space.  The idea is used in **Linear
Algenbra** and **Fourier transform**.

Chunking strategies and vector databases both affect the search result
a lot.

To adapt to different search needs and application scenarios, advanced
RAG techniques are invented.

# Agent configuration, sub-agents, and multi-agents

When we say "create an agent" in a coding agent like Claude or Codex
or a library like LangGraph or CrewAI, we are talking about a
**configuration**.

The configuration usually includes the core instructions (system
prompts), allowed tools, model selection and parameters, and hooks.

In an agent program, given a configuration, the program makes LLM API calls.

```python
def llm_call(user_msg, config) -> result:
  result = llm_api_call(user_msg, config.system_prompt,
                                  config.model_name,
                                  config.model_parameters,
                                  list_of_tool_definitions(config.allowed_tools_list))
  return result
```

The simplest agent is a single LLM API call.

```python
response = llm_call(user_message, agent_config)
```

If we add a `Read-Evaluate-Print-Loop` (`REPL`) to handle user inputs
or external triggers, it is a complete user-facing agent program.

```python
def agentic_compute(user_msg, config) -> result:
  response = llm_call(user_msg, config)
  return result


config = load_initial_agent_config()

#------ REPL ------
while True:
  user_input = read(source)        # ← Man-in-the-Middle happens here
  result = agentic_compute(user_input, config)
  print(result)
#------------------
```

This is the outer loop of a typical agent program.  Note that
Man-in-the-Middle happens after each `agentic_compute` completes.

Now let's focus on `agentic_compute`.

If we add an `if-else` it is an agent with simple harness.

```python
def agentic_compute(user_msg, configs: list) -> result:
  if condition_1:
    response = llm_call(user_msg, configs[0])
  else:
    response = llm_call(user_msg, configs[1])
  return response
```

A more complicated workflow example:

```python
def agentic_compute(user_msg, configs: list) -> result:
  frag_1 = fetch_something()
  resp_1 = llm_call([user_msg, frag_1], configs[0])
  
  frag_2 = fetch_another()
  resp_2 = llm_call([user_msg, frag_2], configs[1])
  
  resp_3 = llm_call([user_msg, resp_1, resp_2], configs[2])

  v = validate(resp_3)

  if v.is_good():
    return resp_3
  else:
    return Result(resp_3, v.validation_result())
```

If we add an inner loop in the program, this is the prototype of a
typical autonomous AI agent.

```python
def agentic_compute(user_msg, config) -> result:
  msg_list = [user_msg]

  while True:
    response = llm_call(msg_list, config)

    # If "end_turn", LLM thinks that the user's goal is reached
    # OR it needs human's input (Man-in-the-Middle).
    if response.stop_reason == "end_turn":
      return response

    # If "tool_use", LLM needs more info from the tools for
    # the next response.
    elif response.stop_reason == "tool_use":
      tool_results = []
      for tool_use in response:
        # !!! HOOK
        # e.g. Block dangerous operations, require approval,
        # modify tool input
        config.pre_tool_hook()

        res = dispatch_tool(tool_use.tool_name, tool_use.args)

        # !!! HOOK
        # e.g. Run formatters, log results, trigger follow-up actions
        config.post_tool_hook()

        v = cleaned_tool_result(res)   # validate or clean the result

        tool_results.append(v)
      msg_list.append(tool_results)

    elif response.stop_reason == "max_tokens":
      raise RuntimeError()

    elif response.stop_reason == "stop_sequence":
      return response

    else:
      raise RuntimeError()

# This example assumes 5 tools available
def dispatch_tool(name, input_args) -> result:
  if name == "get_order_status":
    return get_order_status(**input_args)

  if name == "cancel_order":
    return cancel_order(**input_args)

  if name == "Agent":
    return agentic_compute(**input_args)  # !!! RECURSION, SUB-AGENT

  if name == "Remote_Agent_1":
    # Agent2Agent protocol (A2A):
    # - HTTP/HTTPS transport and optionally Server-Sent Events (SSE)
    # - JSON-RPC 2.0 as the HTTP payload
    return call_remote_agent_1(**input_args) # !!! REMOTE SUB-AGENT

  if name == "Bash":
    skill_meta_and_prompt = bash_cmd(**input_args)  # e.g. Load SKILL.md
    return skill_meta_and_prompt

  return f"Unknown tool: {name}"
```

As we stated before, in `agentic_compute`, you can use `if-else` in
any form, you can even explicitly (programmatically,
deterministically) recursively call `agentic_compute` with a different
configuration (That is a sub-agent!), you can also wrap
`agentic_compute` in a tool (e.g. let's call it "Agent") so that the
LLM can initiate a sub-agent call probablistically.

Combined with prompt engineering, we can produce the popular ReAct
pattern, Chain-of-Thoughts pattern, supervisor pattern, loop
engineering, graph engineering, etc.
